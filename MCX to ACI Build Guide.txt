MCX to ACI Build GuideOct 15, 2026 á @Jonathan ClowesHow each piece of the MCX to ACI interconnect is built on the LD5 and LD8 EX4650 and in ACI, why it is there, and the config to use.  Each section ends with a question to test yourself.How it fits togetherEach link has four layers.  Build them bottom up and check each one before moving to the next.1. Physical: four fibres per ACI link.  Each leaf connects to two different switches in the EX4650 stack (FPC 0 and FPC 1)2. Bundle: on the leafs the four links are a vPC.  On the EX4650 they are one ae.  LACP runs between them3. VLAN and IP: the link VLAN (for example 725) is tagged across the bundle.  ACI puts an SVI on it (side A, side B and a shared secondary).  The EX4650 puts an irb on it in mcx_vrf with the .1 address4. BGP: each leaf runs an eBGP session to the EX4650 irb.  So two sessions per ACI linkThe EX4650 already peers iBGP with the VDOMs, so once routes are allowed through, anything learned from the leafs reaches the rest of MCX over those existing sessions.  Nothing changes on the FortiGates for the build.Test yourself: if LACP is up but BGP won't come up, which two layers would you look at first?Values used in this guideThe examples use LD5 to SWI. The four ports become members of ae30, and from then on you configure ae30, not the ports.set interfaces xe-0/0/20 ether-options 802.3ad ae30set interfaces xe-1/0/20 ether-options 802.3ad ae30set interfaces xe-0/0/21 ether-options 802.3ad ae30set interfaces xe-1/0/21 ether-options 802.3ad ae30set interfaces ae30 description to_SWI-1701-1702-vpcset interfaces ae30 aggregated-ether-options minimum-links 1set interfaces ae30 aggregated-ether-options lacp passiveset interfaces ae30 aggregated-ether-options lacp periodic slowWhat each line does:¥ ether-options 802.3ad ae30: puts the port in the bundle.  Members on FPC 0 and FPC 1 means losing one switch in the stack only loses half the links¥ description: follows the existing style on ae13 (to_<device>-<far end>)¥ minimum-links 1: the ae stays up as long as one member is up¥ lacp passive: matches ae13 and ae23.  Passive only answers LACP, it never starts it, so the ACI side must be active.  If both ends are passive the bundle never forms¥ periodic slow: LACP hellos every 30 seconds.  Fine here as BFD does the fast failure detectionThe total number of ae's must stay within chassis aggregated-devices ethernet device-count (20 today).Test yourself: the ACI port-channel policy is set to LACP passive by mistake. The irb is the layer 3 interface on that VLAN, the same idea as an SVI on Cisco, and it goes into mcx_vrf so it's part of the routing that already talks to the VDOMs.set vlans MCX_ACI_SWI_725 vlan-id 725set vlans MCX_ACI_SWI_725 l3-interface irb.725set interfaces ae30 unit 0 family ethernet-switching interface-mode trunkset interfaces ae30 unit 0 family ethernet-switching vlan members MCX_ACI_SWI_725set interfaces irb unit 725 description MCX_ACI_SWIset interfaces irb unit 725 family inet address 10.158.240.241/29set routing-instances mcx_vrf interface irb.725What each part does:¥ vlans ... vlan-id 725: creates the VLAN.  The name is local to the switch, the ID is what goes on the wire and must match the ACI encap¥ l3-interface irb.725: ties the VLAN to its irb.  Without this the VLAN is layer 2 only¥ interface-mode trunk: the ae sends the VLAN tagged.  ACI expects tagged frames because the L3Out SVI uses encap vlan-725¥ irb unit 725: the unit number matches the VLAN ID by convention only.  Check how the existing irbs are numbered and follow that¥ routing-instances mcx_vrf interface: without this the irb sits in the global table, not mcx_vrf, and BGP in mcx_vrf can't use itMTU is 1500 on both ends, which is the default here, so nothing to set.  Check the VLAN names follow the existing naming (show configuration vlans | display set | match vlan-id) and adjust before the change.Test yourself: you forget the routing-instances mcx_vrf interface irb.725 line. The group name follows the existing mcx-...-peers style.set policy-options policy-statement DENY-ALL term all then rejectset routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers type externalset routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers peer-as 64631set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers neighbor 10.158.240.242 description SWI-1701set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers neighbor 10.158.240.243 description SWI-1702set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers authentication-key "<MD5 key>"set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers bfd-liveness-detection minimum-interval 300set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers bfd-liveness-detection multiplier 3set routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers import DENY-ALLset routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers export DENY-ALLWhat each part does:¥ type external, peer-as 64631: eBGP to the SWI fabric.  The local AS comes from mcx_vrf (routing-options autonomous-system 64635), so you don't set it here¥ neighbor: the side A and side B addresses, not the secondary.  The secondary is shared by both leafs and isn't used for peering¥ authentication-key: MD5.  The same key goes on the ACI BGP peer.  A mismatch shows as the session stuck in Active or Connect¥ bfd-liveness-detection: BFD every 300 ms, down after 3 misses, so about 1 second to detect a failure.  ACI needs BFD enabled on its side too¥ import and export DENY-ALL: nothing in, nothing out.  The sessions come up but carry no routesWhy deny-all matters on this switch.  Your show bgp summary showed Default eBGP mode: advertise - accept, receive - accept.  That means on this Junos version an eBGP session with no policy sends and accepts everything.  Without DENY-ALL, the moment the session came up the EX4650 would send the whole MCX table (~590 routes) to the fabric and take whatever the fabric sends back.  Always apply an explicit policy to eBGP here.Test yourself: the session to 10.158.240.242 is Established but show route receive-protocol bgp 10.158.240.242 shows nothing. Think of it as a chain where each piece points at the next:VLAN pool > L3 domain > AEP > vPC policy group > interface selector on the leaf profileAll under Fabric > Access Policies in the APIC.  SWI shown, UXB is the same with UXB names and VLANs 727-728.1. VLAN pool (Pools > VLAN): SWI_L3OUT_MCX_VLP, static allocation, range 725-726.  The L3Out encap must be in a pool the L3Out's domain uses, or the interface won't deploy2. L3 domain (Physical and External Domains > L3 Domains): SWI_MCX_L3OUT_DOM, pointing at the pool above.  The L3Out references this domain3. AEP (Policies > Global > Attachable Access Entity Profiles): SWI_MCX_AEP, with the L3 domain attached.  The AEP is what links a set of ports to the domains allowed on them4. Port-channel policy (Policies > Interface > Port Channel): LACP active.  There's probably one already, so reuse it.  Active here because the EX4650 side is passive5. vPC policy groups (Interfaces > Leaf Interfaces > Policy Groups > VPC Interface): one per MCX site, because each site is a separate bundle:o SWI_MCX_LD5_VPC_IPG: link level policy to match the optic speed, port-channel policy LACP active, AEP SWI_MCX_AEPo SWI_MCX_LD8_VPC_IPG: the same6. The prefix lists are placeholders until the agreed prefixes are signed off.LD5 EX4650: what goes to the leafsset policy-options prefix-list MCX-TO-ACI <agreed MCX prefixes>set policy-options community LD5-PREF members 64635:100set policy-options as-path FROM-FABRICS ".* (64631|64633) .*"set policy-options as-path FROM-LD8 ".* 64636 .*"set policy-options policy-statement MCX-TO-ACI term no-fabric-transit from as-path FROM-FABRICSset policy-options policy-statement MCX-TO-ACI term no-fabric-transit then rejectset policy-options policy-statement MCX-TO-ACI term from-ld8 from prefix-list MCX-TO-ACIset policy-options policy-statement MCX-TO-ACI term from-ld8 from as-path FROM-LD8set policy-options policy-statement MCX-TO-ACI term from-ld8 then acceptset policy-options policy-statement MCX-TO-ACI term ld5-pref from prefix-list MCX-TO-ACIset policy-options policy-statement MCX-TO-ACI term ld5-pref then community add LD5-PREFset policy-options policy-statement MCX-TO-ACI term ld5-pref then acceptset policy-options policy-statement MCX-TO-ACI term last then rejectJunos reads the terms top to bottom and stops at the first match, so the order is the logic:1. no-fabric-transit: anything with a fabric ASN in the path is rejected first.  This stops SWI routes going to UXB and the other way round2. from-ld8: agreed prefixes that came via LD8 are sent untagged.  This is what stops LD8-only prefixes being preferred via LD53. ld5-pref: everything else agreed is tagged 64635:100, so ACI prefers LD5 for shared prefixes4. last: nothing else goes outLD8 EX4650 uses the same policy without the community: drop the from-ld8 term and change ld5-pref to just accept.Both EX4650: what comes in from the leafsset policy-options route-filter-list ACI-SWI-IN <SWI BD ranges> upto /32set policy-options policy-statement ACI-SWI-IN term bd from route-filter-list ACI-SWI-INset policy-options policy-statement ACI-SWI-IN term bd then acceptset policy-options policy-statement ACI-SWI-IN term last then rejectset routing-instances mcx_vrf protocols bgp group mcx-aci-swi-peers family inet unicast prefix-limit maximum <n> teardownupto /32 lets the BD subnets and their host routes in.
